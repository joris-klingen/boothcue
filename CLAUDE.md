# BoothCue

A singer display for tracking in Ableton Live, built as a VST3 + Standalone
(JUCE 8, macOS first; it also builds on Linux, which is what CI runs). It reads
the linked `.als` (sections from the `parts` track, notes for chord detection)
and shows lyrics, chords, the song position and a count-in on a separate
window. It follows the conventions of `../flashroll` and `../hitnotedmx`
(layout, tools as CTests), with harmeq's plugin identity and CI.

## Finding things

- **What's in a `.als`** (parts, clip colours, MIDI notes and clip timing):
  `Source/AlsParser.{h,cpp}`. The XML paths follow `bbb_code`; ALSmuse is the
  cross-check (`tools/alsmuse_crosscheck.py`).
- **Which chord sounds where**: `Source/Chords.{h,cpp}` (the detector,
  `ChordSettings` holds every tuning constant) and `Source/SetChords.{h,cpp}`
  (a parsed set -> detector input, track roles from names).
- **What line is sung when, count-ins, tap-along, bar.beat formatting**:
  `Source/Song.{h,cpp}`.
- **The text formats**: lyrics in `Source/LyricImport.{h,cpp}`, chord charts in
  `Source/ChordChart.{h,cpp}`, chords as MIDI in `Source/ChordMidi.{h,cpp}`.
- **What the display shows at a position**: `Source/Prompter.{h,cpp}`
  (`buildScene`); how it's drawn: `Source/PrompterPainter.{h,cpp}`; colours and
  Live's clip palette: `Source/Theme.h`.

## Invariants

- **BoothCue never writes the `.als`.** It reads it for structure and chord
  detection; its own lyrics and chords live in the plugin state and in text /
  MIDI files the user saves.
- **In a linked song folder BoothCue only writes `timings.txt`.** `lyrics.txt`
  and `chords.txt` belong to the songbook (`../bovenburen_manager`) and are
  only read (`pollSongFolder`, once a second on the message thread).
- The core (`AlsParser`, `Chords`, `SetChords`, `Song`, `LyricImport`,
  `ChordChart`, `Prompter`, `Transport.h`) stays **plain C++ with no JUCE and
  no clock**: every query takes the position. It builds as `boothcue-core`,
  also with `-DBOOTHCUE_BUILD_PLUGIN=OFF`.
- **The audio thread only copies the playhead** into `SharedTransport`
  (lock-free seqlock) and passes the audio through. No allocations, no locks,
  also when bypassed.
- The `.als` is read and chords are detected on the `SetWatcher` thread; its
  reports are applied by the processor's 10 Hz message-thread timer.
- `getStateInformation` writes from a snapshot under a lock (hosts call it off
  the message thread); `setStateInformation` off the message thread is
  applied by the timer. No automatable parameters.
- Detected chords never overwrite edited ones (`chordsEdited`); "Use detected"
  is the only way back.
- Always build both plugin targets (plain `cmake --build build` does) so the
  VST3 and the Standalone never diverge. VST3 only, no AU.

## Build & verify

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j8
ctest --test-dir build      # als-parser, chord-detect, song-logic, prompter-render, set-watcher, plugin-smoke
```

On Linux the editor / display tests need a desktop session: `Xvfb :99` plus a
window manager (`openbox`; a bare Xvfb fails with BadAtom), `DISPLAY=:99`.
pluginval (strictness 10) is part of CI.

Looking at it without a host:

```sh
./build/prompter-render_artefacts/Release/prompter-render previews/prompter-sheet.png      # display scenes, incl. iPad sizes
./build/prompter-render_artefacts/Release/prompter-render --set set.als lyrics.txt out.png [beat ...]
BOOTHCUE_EDITOR_PNG=editor.png ./build/plugin-smoke tests/fixtures   # also editor-chords.png
```

The screenshots in `docs/` come from these: `prompter-render --set` with one
beat, and `plugin-smoke` with `BOOTHCUE_EDITOR_SET`, `BOOTHCUE_EDITOR_LYRICS`
and `BOOTHCUE_EDITOR_BEAT` pointing at a real set.

Real sets stay out of the repo (private, large). `tests/fixtures/*.als` are
generated by `tools/make_fixtures.py`; `tests/fixtures/lyrics/` holds band
lyrics used as import test cases.

## Releasing

CI builds on Linux only; the Mac build is made and tested locally. Release =
on the Mac: configure Release, build, `ctest`, then put
`BoothCue_artefacts/Release/VST3/BoothCue.vst3`,
`BoothCue_artefacts/Release/Standalone/BoothCue.app` and
[installer/install.command](installer/install.command) in one folder (zip it
to share). Double-clicking `install.command` installs from the folder it sits
in. Bump `project(BoothCue VERSION ...)` in `CMakeLists.txt` and add a
changelog entry in STATUS.md.
